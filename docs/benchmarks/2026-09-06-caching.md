# PostgreSQL-first optimization and isolated Redis evidence

Date: 2026-09-06. This is **local-development evidence**, not a production latency SLO or observed production cache hit rate. No production Redis was deployed. See [architecture and operations](../CACHING.md) and [Next.js freshness audit](../FRONTEND_CACHE_FRESHNESS.md).

**Recommendation: DEFER production Redis until scale/traffic justifies it.** P0 captures the dominant database-work reduction. The local indicator pilot provides meaningful additional latency/CPU benefit at high reuse, but saves no SQL queries and does not justify another service at the current audited cost/unknown traffic level. The pilot remains optional and disabled by default.

[Machine-readable evidence](2026-09-06-caching-results.json) contains all selected run summaries, first-use observations, final-run source fingerprints, response hashes and raw-log SHA-256 values. Full raw JSONL and test logs remain in the local audit artifact directory `C:/Users/manan/AppData/Local/Temp/stockviz-cache-audit-20260906/`. The temporary directory is not a durable repository artifact; retain/export it if raw-sample preservation is required.

## Method and dataset

[`benchmark_reads.py`](../../apps/api/scripts/benchmark_reads.py) exercises actual FastAPI endpoints through TestClient, with SQLAlchemy cursor instrumentation and an ASGI response-body timer. It forces PostgreSQL connections read-only, disables scheduler/Sentry/rate-limiting only in the throwaway benchmark process, and refuses unsuccessful responses. It selects an already-populated portfolio; no benchmark records or provider traffic were fabricated. Existing running API/web services were not patched or deployed.

- Local PostgreSQL 16; 75 symbols, 278,484 price bars, 12 positions and 370 snapshots overall. Selected existing portfolio: six USD equity positions and 120 snapshots.
- Latest local bars end 2026-07-03. This is stale development data, not current market prices.
- News articles, sentiment rows and option positions were empty. **No populated news/sentiment/options performance claim is supported.** Financial options/FX behavior is covered by correctness fixtures, not presented as a throughput benchmark.
- P0: 300 observations per path, 10 warmups, deterministic randomized interleaving, concurrency one. p50/p95 use nearest rank. No p99 claim from 300 observations.
- P1: dedicated AAPL/NVDA indicator workload, 1,000 observations per symbol for off/on/outage, plus 300 cold misses per symbol. Four existing indicators, 252 bars. Repetition is controlled to measure reuse, not organic user behavior.
- ASGI latency runs through the final response body; it excludes external HTTP/TLS/browser time. DB time is cursor execution wall time, including DB network/driver, not pure PostgreSQL CPU. Application CPU is endpoint thread CPU (including ORM/driver) plus completed Redis-worker CPU where applicable; it excludes FastAPI dependencies and response-serialization CPU. Timed-out DNS work can finish after a request, so outage CPU attribution is not a whole-process energy measurement.
- The portfolio-pair row is **summed serial API work**, not a claim that browsers previously waited for two serial requests. The frontend previously fanned them out concurrently but performed both valuations.
- First-use observations have a warm operating-system/PostgreSQL cache. No cold-disk or production cache-flush experiment was performed.

Pre-change image source matched baseline commit `a259f71`; post-change runs copied the actual working source into separate containers. Read-only bind mounting failed in Docker Desktop, so source copies were used. Baseline endpoint-CPU instrumentation was corrected and the full pre-change run repeated; the earlier zero-CPU run is not used below. P1 socket-only outage results are also superseded by the bounded-command implementation.

Warm p50 is about 53% lower and p95 about 55% lower, with approximately 8.5–8.6 ms less application CPU. Redis provides **zero query reduction and no claimed DB-time reduction**; the small DB timing movement is measurement variability, not avoided SQL. p99 has only approximately ten tail observations per symbol and remains local evidence, not a production SLO.

Cold Redis adds approximately 1.9–2.0 ms median overhead compared with no Redis. Its p95 can be worse. This is an important reason not to infer production benefit without traffic/reuse data.

### Hit ratio, memory and correctness

- Warm run: **2,020 hits / 2,022 total lookups = 99.901%**, including first-use and warmups. All 2,000 timed requests hit. Cold run: 0/622 hits including first-use/warmups. These are deliberately controlled repeat/miss workloads, **not expected organic hit rates**.
- Warm cache: two keys use **164,144 bytes** by `MEMORY USAGE` (approximately 80.15 KiB each). Redis reports 846,504 bytes used memory and **13,828,096 bytes RSS** (13.19 MiB), zero evictions and one connected client at inspection. Server memory includes allocator/process costs and cannot be inferred from key bytes alone.
- Illustrative capacity, not measurement: 75 symbols × 10 window/name combinations at that measured key size is approximately 58.7 MiB of key allocation, before server overhead, concurrent old/new content generations and other variants. A 128 MiB maxmemory cap bounds Redis data growth; LRU eviction makes excess variants misses, not durable data loss.
- 2,024 commands took 913.65 ms cumulative caller-observed command wait (about 0.451 ms/command); Redis-client worker CPU totaled 387.19 ms. These worker costs are included in the application CPU figures above.
- All P0/off/warm/cold response hashes match for both symbols; payload sizes remain **60,057 bytes AAPL** and **59,818 bytes NVDA**. Caching changes neither response shape nor values.
- Historical correction without a new latest timestamp changes the key; rollback preserves the old committed key. Tests exercise the existing market-ingest event handler, committed correction, rollback, namespace separation, schema/key versioning, corrupt values, TTL, concurrent misses, and real Redis deletion/repopulation.

### Redis unavailable and restart

With the disposable Redis stopped, all 2,000 timed requests (plus 22 first-use/warmup calls) succeeded and retained the same payload hashes. AAPL p50/p95 were **16.391/21.957 ms**; NVDA **16.347/23.539 ms**. Both remained two SQL queries, approximately 1.08 ms median DB time and 13.76–13.77 ms median endpoint CPU. There were zero hits, two failed Redis attempts, and 2,022 circuit/unavailable bypasses. The two caller-observed Redis waits totaled **80.638 ms**, consistent with the 40 ms per-command budget; there was no retry on every request. Expected sanitized warnings made PowerShell flag native stderr, but the complete request summaries and hashes were produced without an HTTP failure.

The earlier socket-only implementation accumulated approximately 2.64 seconds in stopped-container DNS lookups; it was corrected and remeasured, not retained as acceptable fallback. Unit tests additionally hold a command blocked past the caller timeout and verify that the executor admits at most eight outstanding commands. Background OS DNS work can still delay interpreter shutdown; no normal request waits for that completion.

Redis restart reported **DBSIZE 0** (no persistence). A second complete repeat run then produced two misses, 2,020 hits, two rebuilt keys, zero cache errors and matching payloads. All final off/on/cold/outage/restart API source fingerprint maps are identical. The cache can disappear without losing financial data.

## Reproduction

Use a **populated local development database** and a separate process with the locked API dependencies. Never point this harness at production. Run it from `apps/api` with your local `DATABASE_URL`; outputs are JSONL:

```powershell
$env:BENCH_SAMPLES = '300'
$env:BENCH_OVERVIEW = '1'
.venv/Scripts/python.exe -B scripts/benchmark_reads.py > p0.jsonl
```

For a Redis comparison, keep the same dataset, source, interpreter and workload, and run sequentially with `CACHE_BACKEND=none`, then `redis` using the documented local credentials. Use a dedicated `CACHE_NAMESPACE`, `BENCH_PATHS=AAPL_indicators,NVDA_indicators`, and `BENCH_SAMPLES=1000`. `BENCH_COLD=1` clears **only that configured namespace** before each untimed request boundary; it is for isolated cold-miss experiments, not shared or production Redis. Warm DB is unchanged. Stop/restart only your disposable Redis service to test fallback/recovery. Never use `FLUSHALL`.

Record the source revision/diff, machine/runtime/data counts, first-use records, per-request raw rows, summaries, hashes, cache counters and Redis memory. Compare hashes before interpreting latency. The JSONL includes normalized payload hashes and refuses non-200 measurements. Query cursor time is not a substitute for `EXPLAIN (ANALYZE, BUFFERS)`; the original audit's lateral SQL experiment also showed zero temporary spill and roughly 450 shared buffer hits versus approximately 5,469 and temporary spill for the whole-history window scans.

## Cost model (not a bill forecast)

The read-only deployment audit found one Railway API replica and PostgreSQL primarily paying idle memory/storage, with a nightly cron and separate web. The Kubernetes manifests allow API horizontal scaling; local caches are not assumed globally coherent. Production traffic/reuse was **not measured reliably**, and the deployed source was older than the local audit tree.

Railway's published resource rates used by the audit are approximately $10/GB-month RAM and $20/vCPU-month, with private service networking avoiding public egress. A dedicated 64–128 MiB average-RSS Redis plus 0.001–0.01 average vCPU is roughly **$0.66–$1.48/month**; 256 MiB RSS is roughly $2.58–$2.76/month. This is a resource scenario, not a managed-Redis quote, fixed allocation price, HA/SLA promise, or proof that Railway's Redis template is managed. Verify rates and deployment terms before any future approval. [Railway pricing](https://docs.railway.com/pricing/plans), [Redis deployment documentation](https://docs.railway.com/databases/redis).

The audit observed only about $0.0054 in combined API/PostgreSQL CPU charges during the sampled partial billing period (roughly $0.024/month if linearly extrapolated). That is not enough CPU expenditure to fund another always-on service. P0 requires no new infrastructure and removes unnecessary DB work; lower utilization may create headroom without reducing an idle-memory bill.

For a deliberately simplified future scenario, saving 8 ms of API CPU per hit saves only about **$0.062 per million hits** at $20/vCPU-month and 30 days/month. Roughly **11–24 million hits/month** would be needed just to offset the $0.66–$1.48 Redis scenario, before its command CPU, misses, network, monitoring or operational work. Avoiding an entire extra API replica could be more valuable, but that requires load/capacity evidence not present here. Low traffic favors P0 and existing materialization; future high repeat traffic may justify the latency benefit independently of bill reduction.

Local pilot cloud cost is $0 incremental because no cloud service was provisioned; local machine resource use is not claimed free. Private caches, distributed locks/rate limits, provider caches and production sizing are not inferred from this experiment.
